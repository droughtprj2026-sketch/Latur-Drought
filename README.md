# Latur Drought Intelligence Platform

Real-Time Drought Monitoring — Latur District, Marathwada (2016–2026).

A full-stack platform that ingests Sentinel-2 + CHIRPS rasters, computes drought indices (SPI, NDVI, EVI, PCI, VHI → CDI) in Python, stores them in Supabase (Postgres + PostGIS), serves them through a Node.js API gateway, and renders maps (Leaflet) and time-series charts (Recharts) in a Next.js frontend.

## Architecture

### Data Pipeline

```
Raw Rasters (Sentinel-2 + CHIRPS)
        ↓
historical/latur_chirps_spi.py      → SPI-1/3/6/12 reference rasters
historical/build_village_indices.py → NDVI/EVI/VCI/VHI rasters + village zonal stats
historical/composite_cdi.py         → Fuses SPI + NDVI + EVI + VCI + VHI + PCI → CDI
realtime/orchestrator.py            → Near-real-time satellite ingestion, QC & atomic JSON updates
historical/dashboard_master.py      → Builds data/dashboard/ + frontend/public/data/
```

### API Flow

```
Python Pipeline → data/dashboard/ → frontend/app/api/v1/[...slug]/route.ts → Frontend
```

The API route reads JSON files from `data/dashboard/` with mtime-based cache invalidation, so the frontend always gets fresh data when the pipeline runs.

### Data Flow per Period

1. **CHIRPS**: Monthly rainfall → `latur_chirps_spi.py` → SPI-1/3/6/12
2. **Sentinel-2**: Monthly composites → `build_village_indices.py` → NDVI/EVI/VCI/VHI rasters + village zonal stats
3. **Composite**: `composite_cdi.py` → Weighted fusion → CDI score (0–1) + D-code class
4. **Dashboard**: `dashboard_master.py` → Writes `data/dashboard/` + `frontend/public/data/`
5. **API**: Node.js gateway reads `data/dashboard/` files → Serves frontend
6. **Frontend**: Next.js + Leaflet + Recharts → Renders map, charts, tables

## Running the Pipeline

### Local Development

```bash
cd E:\Drought\scripts
python dashboard_master.py
```

This runs the full pipeline:
1. `build_village_indices.py` — NDVI/EVI/VCI/VHI rasters + village zonal stats
2. `composite_cdi.py` — CDI fusion
3. `dashboard_master.py` — Dashboard outputs + SQLite
4. `build_baseline_drought.py` — Baselines + SQLite

### GitHub Actions (Weekly Realtime Sync)

The `realtime_drought_sync.yml` workflow runs weekly on Mondays at 02:00 UTC:
1. Authenticates to Google Earth Engine (service account)
2. Runs `chirps_gee.py` — CHIRPS rainfall from GEE
3. Runs `pipeline_gee.py` — Sentinel-2 from GEE + zonal stats
4. Runs `composite_cdi.py` — CDI fusion
5. Runs `dashboard_master.py` — Dashboard outputs
6. Syncs to Supabase + GitHub

Required GitHub Secrets:
- `GEE_PROJECT` — Google Cloud Project ID
- `GEE_SERVICE_ACCOUNT_KEY` — GCP Service Account Key JSON
- `SUPABASE_URL` — Supabase project URL
- `SUPABASE_SERVICE_ROLE_KEY` — Supabase service role key
- `DATABASE_URL` — Supabase database URL
- `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` — Vercel deployment

## Key Design Decisions

1. **Single source of truth**: All CDI weights, thresholds, and formula version live in `config/composite.yaml`. Code reads from YAML, never hardcodes values.
2. **Missing data = NaN**: Missing inputs are never filled with zeros. If fewer than `min_inputs` (3) components are available, the period is marked `pending`.
3. **Incremental processing**: Pipeline reads manifests and processes only new/affected periods. A new CHIRPS month retriggers every rolling SPI window that includes it.
4. **Atomic writes**: Manifests are written atomically (`.tmp` → `replace`).
5. **API cache invalidation**: Node.js API reads files with mtime-based cache invalidation, so frontend always gets fresh data when pipeline runs.
